CASE STUDY · QUALITY & DELIVERY

Merging two chat codebases behind a regression harness

The embeddable chat widget lived in its own repository with a copy of the chat UI, so every fix had to be made twice. I moved it into the main bot application behind configuration flags, migrated the build to pnpm, and built a Vitest and Playwright harness to prove customer behaviour did not change.

Context and problem

Customers embed the chatbot with a small loader script that mounts a web component. That widget lived in a separate repository with its own copy of the chat interface, so fixes were made twice and the two copies had drifted apart.

The main bot app also relied on npm hoisting: some code imported packages it never declared, which would break under a stricter package manager.

Requirements

  • One chat implementation for the hosted bot and the embedded widget.
  • The customer embed contract does not change, down to the loader file.
  • The hosted app behaves exactly as before.
  • Builds work in GitHub Actions, Jenkins and Docker.

Constraints

  • The widget renders inside an open Shadow DOM, which changes how styles and popovers behave.
  • The product repositories had no automated test gate, so proving parity needed its own harness.

My responsibilities

  • Designed the configuration approach and moved the widget into the main app.
  • Set up the second build target and the pnpm migration across CI.
  • Built the external regression harness and wrote the verification, smoke-test and rollback plans.

Built with others: The original widget was built by a teammate. DevOps owns the Jenkins and deployment configuration, which is why the plan includes a checklist for them.

Architecture

  • A chat configuration context makes the shared components configurable: API base, link component, tooltip mode and feature flags.
  • The hosted app uses defaults; the widget turns on parity flags.
  • Next.js builds the hosted app as a static export; Vite builds the widget bundle and loader.

Implementation

Configuration over forks

Instead of forking components, the shared chat reads a configuration context. The hosted configuration matches the old hosted behaviour exactly; the widget configuration enables the behaviours customers already had, such as inline tooltips and the server limit message.

A second build target

A Vite configuration builds the widget bundle and loader from the same source tree, with CSS injected into the shadow root and React’s production build.

Declare first, then switch package managers

I first declared every package that strict resolution would have broken, then moved to pnpm 10 with a pinned packageManager field, overrides and a build-script allowlist. CI uses the pnpm store cache and a frozen lockfile in GitHub Actions, an Alpine-based install in Jenkins, and Node 22 in Docker Compose. New scripts run the widget on its own or alongside the hosted app during development.

Key decisions

Inline tooltips in the widget

Why
Radix portals render into document.body, outside the shadow root, so they arrived unstyled.
Tradeoff
Two tooltip modes to maintain, selected by configuration.

Keep known issues out of scope

Why
A scroll flake, a Tailwind variable leak in the shadow root, a broken lint script and a keyboard accessibility gap all existed before. Fixing them here would hide whether the move itself changed anything.
Tradeoff
They are recorded as follow-ups rather than fixed now.

Challenges

Proving that customers would see no difference.
Golden captures of the old widget’s exact API requests, screenshot baselines and side-by-side comparison pages.

Testing and validation

An external Vitest and Playwright harness with golden API-request captures, screenshot baselines in 13 desktop and mobile states, and tooltip and menu comparisons.

In my runs: legacy widget suite 32 of 32, parity suite 21 of 21, hosted unit tests 34 of 34, hosted end-to-end tests 40 of 40 across two runs.

The loader file is byte-identical to the old one and the hosted CSS is identical. Jenkins steps were dry-run in Alpine on Node 20 and 22.

Deployment

Written before merge: an eight-gate pnpm verification plan, a staging smoke test, a rollback plan using the previous image tag or a merge revert, and a checklist for DevOps.

Outcome

  • The pull request is open and awaiting review. Once merged, chat fixes land once for both the hosted bot and every embedded widget.

What I learned

Write the rollback plan before you ask anyone to merge. It forces you to name exactly what could go wrong.
