CASE STUDY · BROWSER EXTENSION · INTERNSHIP

A Chrome extension for chatting with any web page

People had to copy text out of the page they were reading to ask the company's LLM platform about it. During my internship I designed and built a Manifest V3 extension that reads the page, or the open Gmail message, and streams answers into a chat window beside it, signed in through the company's single sign-on.

Context and problem

The company wanted its LLM platform to be available wherever people were already working, instead of in a separate tab. The requirements asked for a Chrome extension that extracts the visible content of any page, lets the user chat about it or summarise it, and connects to the company's AI services.

It had to work on ordinary websites and inside Gmail, where the open message changes without the page reloading.

Requirements

  • Use the visible content of the current page as context for the conversation.
  • Open a clean chat interface from the toolbar button, a right-click menu and a keyboard shortcut.
  • Stream answers from the company's LLM platform and render them as formatted Markdown.
  • Sign users in through the company's single sign-on rather than a separate password.

Constraints

  • Manifest V3 runs background logic in a service worker that Chrome can stop at any time, so state cannot live only in memory.
  • During development the company's API did not accept requests from the extension's origin (CORS), and changing the server configuration was outside my access.
  • Every website structures its content differently, and Gmail re-renders the open message without a page load.
  • Answers can take a long time to generate, so they have to stream in rather than arrive all at once.

My responsibilities

  • Designed and built the whole extension: background service worker, content script, chat interface and sign-in flow.
  • Wrote a small Node.js/Express proxy server so the extension could reach the company's API during development.
  • Worked from the product requirements document and integrated with the company's existing authentication and chat APIs.

Built with others: This was my internship project. The authentication service and the chat API it calls were built and owned by the company's platform team.

Architecture

  • The content script runs on every page: it extracts the visible text, injects the chat window as an iframe, and highlights text when the chat asks it to find something on the page.
  • The background service worker owns sign-in, per-tab chat sessions and the streaming request to the API.
  • The proxy forwards sign-in, workspace and chat-stream requests from a server, where the browser's CORS check does not apply.

Implementation

Three parts that talk through messages

Manifest V3 splits an extension into isolated contexts, so the content script, the chat window and the background worker coordinate through named messages such as extractContent, openChatIframe, sendChatMessage, stopGenerating and findOnPage. Before opening the chat, the worker pings the page's content script and injects it if it is missing, retrying once a second. Any message that might never be answered, for example because the tab closed mid-request, times out after ten seconds instead of hanging.

The page as context

The content script reads the page's visible text. In Gmail it targets the open message's container, and a MutationObserver re-extracts the content whenever the user switches to another email. The first message of a conversation carries the extracted page content; later messages carry the previous turns, so follow-up questions keep their context.

Sign-in without another password

The worker reads the company's single sign-on access token from its cookie and decodes the JWT to check its expiry before using it. If the token is missing or expired it opens the sign-in page in a popup, retrying up to three times, with an email-and-password form as a fallback. After sign-in it fetches the user's workspace and stores it for later requests.

Streaming answers with a Stop button

The chat request streams Server-Sent Events. The worker reads the response body with a ReadableStream reader and TextDecoder, parses each data line, and the chat window renders the growing answer as Markdown with marked.js. A Stop button aborts the request through an AbortController and keeps the partial answer, and a 60-second limit ends replies that run too long.

Sessions that survive the worker restarting

Conversations are kept per browser tab and saved to chrome.storage, because Chrome can stop a Manifest V3 service worker at any time and in-memory state would be lost. A tab's session is cleaned up when the tab closes, and if the server reports that a session no longer exists, the extension starts a new one and asks the user to resend.

A proxy to get past CORS

The company's API rejected requests coming from the extension's origin. Rather than wait for a server change, I wrote an Express proxy with three routes: sign-in, workspaces and chat stream. It forwards the user's Authorization header and pipes the event stream straight through with response buffering disabled, so tokens still arrive word by word.

Everyday details

Right-click menu entries for chatting about the whole page or just the selected text, a Ctrl/Cmd+M shortcut, copy-to-clipboard on replies, find-on-page highlighting that scrolls to the match, a chat window that resizes to fit its content, and dark mode that follows the page.

Key decisions

A local proxy instead of waiting for a server change

Why
It unblocked development immediately when the API rejected requests from the extension's origin.
Tradeoff
The extension only works while the proxy is running. The production fix is to allow the extension's origin on the API itself.

Chat in an injected iframe instead of the toolbar popup

Why
Chrome closes a toolbar popup as soon as focus leaves it, which would throw away the conversation. An iframe stays beside the page.
Tradeoff
The iframe and the page have to coordinate its size and theme through messages.

Persist sessions in chrome.storage

Why
The Manifest V3 service worker can be stopped at any moment, taking in-memory state with it.
Tradeoff
Every read of session state is asynchronous, which makes the message handlers more involved.

Check token expiry before calling the API

Why
Decoding the JWT's expiry locally avoids sending a request that is certain to fail.
Tradeoff
The server can still reject a token, so 401 responses are handled as well.

Challenges

Gmail changes the open email without reloading the page.
A MutationObserver on the message container re-extracts the content whenever it changes.
On some pages the chat opened before the content script was ready to receive messages.
The worker pings the content script, injects it when there is no answer, and retries once a second.
Requests to the company API were blocked by CORS.
A small Node.js proxy made the calls from a server and streamed the responses back.

Testing and validation

Testing was manual, with the unpacked extension in Chrome talking to the company's API through the proxy. There were no automated tests. Unit tests for the message handlers and the stream parser are the first thing I would add.

Deployment

Run as an unpacked Chrome extension, with the proxy server running locally alongside it.

Outcome

  • A working extension that chats about any web page or Gmail message, streams answers from the company's LLM platform, and signs users in through company single sign-on.
  • Reachable from the toolbar, the right-click menu and a keyboard shortcut.

What I learned

A browser extension is a small distributed system: isolated contexts, any of which can disappear, talking through messages. Every message needs a timeout and every piece of state needs a home that survives restarts.

A proxy is a fine way to unblock development, but it should not log what passes through it. Mine printed full sign-in responses to the console, which I would remove.
