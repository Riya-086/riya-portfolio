CASE STUDY · BACKEND & PLATFORM

Organization- and team-scoped variables with encrypted secrets

Teams were pasting the same credentials and endpoints into every AI workflow. I delivered shared variables at organization, team and personal scope end to end: an encrypted store, runtime resolution that keeps secrets out of run output, admin and builder UIs, and Kafka-driven cache invalidation.

Context and problem

Workflows on the platform could only use variables defined inside the workflow itself, plus a fixed set of system values. Anything shared, such as SMTP credentials, service endpoints or API keys, had to be copied into every workflow that needed it, with nowhere safe to keep a secret.

Requirements

  • Variables at organization, team and personal scope, referenced in workflows as placeholders like {{ORG.NAME}}.
  • Secret values encrypted at rest, decrypted only on the server, and never returned by the API or shown in run output.
  • Access checks so users only see their own teams’ and their own personal variables.
  • Available everywhere workflows read configuration.
  • Services that cache configuration pick up changes without a restart.

Constraints

  • The workflow engine already had its own variable resolution and secret-masking logic that had to keep working.
  • The model service runs as several pods, each with its own cache.

My responsibilities

  • Python/Quart API, data layer and access checks for the variables.
  • Runtime resolution and masking in the workflow engine.
  • Permission policies in the Spring Boot identity service.
  • The admin settings page and the workflow-builder picker and validation.
  • Kafka events and cache invalidation in the model service.

Built with others: The builder’s inline variable-selector component, which my picker plugs into, was built by a teammate. The workflow engine itself predates this work.

Architecture

  • One scope-parameterised REST API serves organization, team and personal variables.
  • The workflow run service asks for the resolved set at the start of a run.
  • Variable changes publish metadata-only events; the model service invalidates its versioned cache when one arrives.

Implementation

One API instead of three

My first version had a separate resource per scope. Within the same epic I refactored it into a single API with a scope parameter, which made name uniqueness across all three namespaces one check instead of three, and gave the front end one client. Listing with scope=ALL returns organization variables, the caller’s personal variables and only the caller’s teams.

Encrypt on write, decrypt only at run time

Secret values are encrypted with the platform’s shared AES cipher before they are stored. Reads through the API return a masked placeholder. Decryption happens only inside the server-side resolution step.

Resolution that respects existing rules

At the start of a run, the resolved variables are merged underneath the workflow’s own static values, so a workflow-level value always wins. The names of secret variables are added to the engine’s existing masking set, so a decrypted secret can never appear in run output. A disabled or missing reference logs a warning instead of failing the run.

Admin and builder interfaces

The settings page validates with a Zod schema: names must be valid identifiers, values are limited to 4,000 characters, a team is required for team scope and locked after creation, and a secret is only re-entered when explicitly replaced. In the builder, organization and team variables appear as their own groups in the picker, inactive ones are greyed out, and validation waits for the first fetch to settle so the canvas never flashes false errors. The ORG., TEAM., PERSONAL. and SYSTEM. prefixes are reserved and rejected for workflow-level variable names.

Variables everywhere configuration is read

I extended resolution to email action providers, sub-workflows, the single-node test runner, MCP server requests, webhook outputs and LLM provider parameters.

Cache invalidation across pods

Variable changes publish metadata-only Kafka events, so no values travel over the bus. The model service caches provider configuration per pod, and a shared consumer group delivered each event to only one pod. I suffixed the consumer group with the host name so every pod receives every event and invalidates its own versioned cache.

Key decisions

Warnings instead of blocking saves

Why
I first built a save-time block for references to disabled variables and a delete guard for variables in use. The product decision was to warn rather than block, so I removed both and surfaced warnings in the builder and on the canvas.
Tradeoff
A deleted variable resolves to empty at run time, so the warnings have to be easy to see.

Metadata-only events

Why
Consumers only need to know something changed; putting values on the bus would spread secrets to every subscriber.
Tradeoff
Consumers re-read from the source of truth after an event.

Per-pod consumer groups

Why
Every pod holds its own cache, so every pod needs every event.
Tradeoff
Each pod processes every event, which is fine for a low-volume configuration stream.

Challenges

Only one model-service pod ever invalidated its cache.
Kafka delivers each event to one member of a consumer group. Giving each pod its own group turned the topic into a broadcast.
The list of reserved variable-name prefixes was silently wrong.
A missing comma had made Python join two adjacent string literals into a single entry. I added the comma.
The settings page made one list request per team the user belonged to.
Replaced the per-team fan-out with a single scope=ALL request.

Testing and validation

Manual testing against a local stack for each scope and access rule, plus local scripts to check placeholder validation in MCP server settings.

Deployment

Merged to development across all six repositories and deployed to staging through the existing pipelines.

Outcome

  • Organization, team and personal variables, including encrypted secrets, are usable across workflows, email actions, sub-workflows, MCP servers, webhooks and LLM provider settings.

What I learned

Know your messaging semantics before relying on them. A consumer group is a work queue, not a broadcast.

A secret has to be tracked as a secret through every stage of a pipeline, not just where it is stored.
