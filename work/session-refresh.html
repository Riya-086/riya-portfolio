CASE STUDY · IDENTITY & SECURITY

Silent session refresh with single-use refresh tokens

Users were being sent back through single sign-on whenever their access token expired. I designed refresh-token rotation in the Spring Boot identity service and a shared session module for the Next.js apps, so sessions renew quietly even with many tabs open.

Context and problem

The platform had recently moved its authentication cookies to HttpOnly, a migration a teammate led. After that change the identity service issued only an access token. Each front end’s “refresh” step re-ran a session check that never minted anything new, so when the access token expired, users were sent back through single sign-on in the middle of their work.

Refresh logic had also been copied into each front end with small differences, so a fix in one app did not reach the others.

Requirements

  • Renew sessions without sending the user back to the login page.
  • Make refresh tokens single-use and detect a token being replayed.
  • Behave correctly when several browser tabs try to refresh at the same moment.
  • Never let a deactivated account renew its session.
  • Give every front end the same session behaviour.

Constraints

  • The identity service runs as multiple replicas, so an in-memory lock would not protect a token.
  • Tokens live in HttpOnly cookies, so browser code cannot read them to coordinate.
  • The shared HTTP client redirected to single sign-on on any 401 before a refresh could be attempted.
  • Browser tabs share cookies but not memory, so two tabs can spend the same token without knowing about each other.

My responsibilities

  • Designed the rotation model and implemented the refresh service and endpoint in the Spring Boot identity service.
  • Wrote the session module used by each front end and the Next.js edge middleware that refreshes during server-side navigation.
  • Shipped follow-up fixes after rollout, including the rate-limit change for multi-tab bursts.

Built with others: This built on a teammate’s HttpOnly-cookie migration and on existing rate-limiting code. Teammates reviewed and merged several of the front-end pull requests.

Architecture

  • Login mints a root refresh token in a new family, bound to the active session.
  • The refresh endpoint verifies the token’s signature before touching the database, reloads the account so deactivated users are rejected, and re-issues both cookies.
  • On the client, one module per app owns the session: it verifies first and refreshes at most once.

Implementation

Spending a token is one atomic operation

A refresh spends the presented token with a single MongoDB findAndModify that only matches if the token has not been used, and in the same write records which token replaced it. Because the condition and the update happen together on the database, two replicas cannot both spend the same token. The successor is minted before this compare-and-set, so no request can ever observe a spent token that has no successor.

Four explicit outcomes

A refresh ends in one of four states. Rotated: the normal case. Reused within grace: the token was spent less than ten seconds ago, so the caller gets the same successor and parallel tabs converge on one session. Replay: the token was spent earlier than that, so the whole token family is revoked in one bulk update and the session is deleted. Invalid: anything else. Every rejection clears both cookies.

One session module per front end

Each app got a session module with a per-tab single-flight promise, a cross-tab lock in localStorage with a short time-to-live, and a broadcast key. When one tab finishes refreshing, the others re-verify instead of spending another single-use token. A timeout covers a tab that dies while holding the lock.

Refresh during server-side navigation

In the apps with edge middleware, a page request with an expired access cookie and a valid refresh cookie triggers a server-side refresh. The middleware rewrites the forwarded cookie header so server components see the new session in the same request, and sets the rotated cookies on the response. It skips API routes on purpose: a second rotation of the same token there would look exactly like a replay. The server-side call has an eight-second timeout, the refresh cookie’s name is derived from the access cookie’s name so a second environment variable cannot drift, and a session that comes back without an organization goes to organization selection instead of an error page.

Follow-ups after rollout

Sessions now have an absolute deadline that successors inherit rather than sliding forward forever. I also restored sessions whose server-side record had expired while a valid refresh row existed, revoked refresh rows when a session is evicted, and changed refresh rate limiting to a per-user key after bursts from many tabs produced 429 responses.

What the server decided, newest first

    Key decisions

    Compare-and-set in MongoDB instead of a distributed lock

    Why
    A conditional findAndModify is atomic per document and already works across replicas, so it needed no new infrastructure.
    Tradeoff
    Correctness depends on getting the condition and the write ordering exactly right, which is why the successor is minted first.

    A ten-second grace window for reuse

    Why
    Legitimate parallel requests from several tabs should converge on one session, not be treated as theft.
    Tradeoff
    For those few seconds a reused token returns a session instead of triggering revocation. Outside the window, reuse revokes the whole family.

    Raw fetch instead of the shared HTTP client

    Why
    The shared client redirected on 401 and dropped the status on 403, so a refresh could never be attempted through it.
    Tradeoff
    The session module carries its own small request helper, documented in the code.

    Copy the module into each app for now

    Why
    Shipping the fix to every app did not have to wait for a shared-library release.
    Tradeoff
    Five copies to keep in sync until it moves into the shared library, which the code comments call out.

    Challenges

    Two tabs refreshing at once could make the second look like an attacker replaying a token.
    Handled on both sides: the grace window on the server, and the single-flight promise, cross-tab lock and broadcast on the client.
    Bursts of refreshes from many tabs hit the per-IP rate limit and returned 429.
    Keyed refresh rate limiting per user, with a looser per-IP flood guard.
    Middleware and API routes could both rotate the same token in one page load.
    The middleware skips API routes, which rotate on their own.

    Testing and validation

    I verified each outcome by hand against a running backend, including the exact 401 and 403 responses the session module depends on, and recorded that behaviour in code comments.

    While building the service I wrote JUnit 5 and Mockito tests for rotation, the grace window, replay, bulk revocation and cookie attributes. They stayed on my machine and were not committed, which is the first thing I would change about how I shipped this.

    Deployment

    Merged into the development branches of the identity service and the front ends; the pipelines build development and update the staging environment.

    Outcome

    • Refresh-token rotation and the shared session behaviour are merged in the identity service and five front-end apps.
    • The cross-tab and rate-limit issues found after rollout were fixed in follow-up changes.

    What I learned

    Browser tabs are concurrent clients racing on shared state, and they need the same care as server replicas.

    Security code needs committed tests. Manual verification proved the design worked once; tests would prove it keeps working.
