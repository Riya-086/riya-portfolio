CASE STUDY · AUTHORIZATION & DATA

Consolidating an authorization model without changing anyone’s access

Permission policies had sprawled into overlapping create, edit and delete variants, and some checks were inverted. I audited the model and consolidated it into view and manage pairs through 45 idempotent database migrations that preserved every user’s effective access.

Context and problem

Over time the identity service had accumulated separate create, edit and delete policies for most capabilities, plus entries nothing used any more. A few checks were wrong in ways that mattered: one read endpoint required the permission to create.

Every front end gated parts of its interface on these policies, so the model could not change in the backend alone.

Requirements

  • Collapse each capability into a view policy and a manage policy.
  • No user gains or loses access as a result.
  • Tokens that were already issued keep working.
  • Front-end gates point at the new policies.

Constraints

  • Issued access tokens reference policies by identifier, so deleting a policy would break decoding of live tokens and reusing an identifier would silently grant access.
  • Migrations run on every environment, so each one has to be safe to run more than once.

My responsibilities

  • Inventoried the existing policies and how endpoints mapped to them.
  • Designed the three-step migration pattern and wrote all 45 migrations.
  • Re-pointed permission checks in six front ends and removed 20 components that no longer had a route to them.

Built with others: The policy mechanism itself predates this work. I changed the policies, their mappings and the grants, not how authorization is enforced.

Architecture

  • Endpoints declare the method they protect, and method-authorization rows map those methods to policies.
  • A role’s grants decide which policies end up in a user’s token.
  • Front ends read the same policies to decide what to show.

Implementation

Step one: add before you remove

Each migration first creates the consolidated policy and maps it to the union of methods its predecessors covered. Nothing is taken away at this point, so an interrupted rollout leaves the system working.

Step two: backfill grants by role

Every role that held a legacy policy for a capability is granted the matching consolidated policy, compared role by role so nobody is granted something they did not effectively have.

Step three: narrow and deprecate, never delete

Only then are method mappings narrowed and the legacy policies marked deprecated. They are never deleted, because their identifiers are still referenced by tokens in circulation.

Thirteen capability families

The pattern covered organizations, users, roles, teams, plans, referrals, apps, MCP servers, templates, files, export, assets and LLM tasks, with the front-end gates updated alongside each family.

Key decisions

Expand, backfill, then contract

Why
At every intermediate step the system is valid, so a partial rollout cannot lock anyone out.
Tradeoff
Three migrations per family instead of one, and a longer series to review.

Deprecate instead of delete

Why
Deleting or reusing a policy identifier would break or silently widen access for tokens already issued.
Tradeoff
Dead rows remain in the database, clearly marked.

Idempotent migrations

Why
Every environment runs them, sometimes more than once; upserts and grant-if-missing make re-runs harmless.
Tradeoff
Slightly more code per migration than a one-shot script.

Challenges

Partway through the series, developer-portal users started receiving 403 responses.
A flag on the original policies that marked them as developer-portal policies had not been carried over to the replacements. I traced it and restored the flag in a later migration in the same series.
One of my migrations collided in run order with a teammate’s migration.
Renumbered mine so the two ran in a defined order.

Testing and validation

Verification was manual, checking access per role before and after each family. The developer-portal regression was found that way and fixed within the series.

Deployment

Merged to development with the front-end gate changes; deployed to staging through the existing pipeline.

Outcome

  • 45 migrations merged, covering 13 capability families.
  • Front-end permission checks in six apps updated, and 20 orphaned components removed.

What I learned

When you replace a record, compare every field, including the ones you think are derived. The 403s came from a flag I had not thought of as part of the policy’s meaning.
