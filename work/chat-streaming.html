CASE STUDY · REAL-TIME & AI

A structured streaming protocol and guardrails for an AI chatbot

The embeddable chatbot rendered broken markdown because its plain-text stream split tokens across network chunks. I moved the backend and two React clients to named Server-Sent Events with a buffered parser, then helped harden the bot runtime with an atomic session cap and grounded follow-up suggestions.

Context and problem

Customers embed the platform’s chatbot on their own sites, and the same chat also runs inside the bot builder. The bot backend streamed plain text chunks. Markdown tokens were split wherever the network happened to break the stream, so the clients rendered broken formatting, and after a change to the platform’s chat API they sometimes showed raw JSON.

Separately, bots ran on an older agent path, would answer off-topic questions, had no limit on session length, and their follow-up suggestions could fail silently.

Requirements

  • A stream that carries typed events, not just text.
  • Clients that render correctly no matter where the network splits the stream.
  • Smooth scrolling while a reply is streaming.
  • A hard cap on interactions per session that cannot be raced.
  • Follow-up suggestions only when the bot’s knowledge base can actually answer them.

Constraints

  • The platform’s main chat already used a structured event format, so the bot stream had to align with it.
  • The main system prompt is cached by the LLM provider; changing it for bots would lose that caching for everyone.

My responsibilities

  • Wrote the backend translation from the old chunk stream to named events.
  • Wrote the buffered parser and event handling in both React clients, plus the scroll behaviour and limit UI.
  • Built the guardrail prompt block, the atomic session cap and the grounded suggestion pipeline.
  • Added per-bot model selection and agent-backed bots across the bot builder, chat service and asset service.

Built with others: The platform’s chat API and the current structure of the streaming client were built by a teammate. Moving bots onto the LangGraph agent runtime was shared work with another engineer.

Architecture

  • A visitor’s message is POSTed to the bot chat endpoint, which runs the agent and streams the reply.
  • The backend emits session.start, text.delta, suggested, file, error and message.end events, plus keep-alive comments.
  • Each client parses frames from a persistent buffer and updates state per event type.

Implementation

Named events on the backend

I added a translation step that turns the legacy chunk stream into named Server-Sent Events. Text arrives as JSON in text.delta events, the session’s id and interaction counters arrive in session.start, and files, errors and suggestions each have their own event.

A parser that keeps the tail

Both clients read the response body as a stream, append decoded bytes to a buffer, split on the blank line that ends an SSE frame, and keep the incomplete last piece for the next read. A frame is only parsed once it is complete, so a split in the middle of a markdown token no longer matters.

Scrolling without fighting the reader

Scrolling on every token pulled the view away from anyone trying to read. I replaced it with a spacer that pushes the new message to the top and shrinks as the reply grows, measured after layout settles using two animation frames.

A session cap that cannot be raced

Each interaction increments the session counter with a single conditional update that only matches while the count is below 20. Two requests arriving together cannot both slip past the limit. When the cap is reached the API returns 429 with a structured code, and the clients show a limit banner. The clients also cap input at 10,000 characters.

Moving bots onto the agent runtime

With another engineer, I routed bot traffic through the platform’s LangGraph ReAct agent service, with a restricted tool allow-list enforced when tools are bound to the agent. Existing encrypted conversation history is decrypted to seed the new transcripts, so sessions in progress carry over.

Guardrails that keep prompt caching

An identity-and-scope block is added to the prompt only for bot requests, so the platform’s main system prompt stays byte-identical and keeps its provider-side cache.

Grounded follow-up suggestions

The model proposes up to five follow-up questions. Each one is checked with a vector search against the bot’s knowledge base, and one LLM verification pass keeps at most three that the content can answer.

Agent-backed bots with per-bot models

Bot owners can now choose a model per bot, where a “default” option stores nothing so existing bots are unchanged, or hand a bot’s turns to a published conversational agent. Saving one mode clears the other mode’s settings. Agent turns run with the bot owner’s access, activity is attributed to the bot rather than a synthetic user, and files the agent generates arrive as file events and render as chips.

Key decisions

Named events instead of richer text chunks

Why
Typed events let the client handle text, files, errors and limits separately, and match the format the rest of the platform already used.
Tradeoff
Backend and two clients had to change together, so the rollout had to be coordinated.

Atomic conditional update for the cap

Why
Read-then-write leaves a window where concurrent requests both see 19.
Tradeoff
The rule lives in the database query, so it has to be read there, not in application code.

Verify suggestions before showing them

Why
A suggestion the bot cannot answer is worse than no suggestion.
Tradeoff
An extra vector query per candidate and one LLM call per reply.

Challenges

SSE frames do not line up with network chunks.
Persistent buffer that carries the incomplete tail across reads.
Per-token auto-scroll jittered and fought the user.
Push-to-top spacer measured after a double requestAnimationFrame.

Testing and validation

Manual testing across both clients against a local backend. A later automated harness for the widget measured a pre-existing 1–3% flake in scroll timing, which is recorded as a follow-up.

Deployment

Merged to development in the backend and both clients; the widget changes up to August 2026 reached the main branch.

Outcome

  • Both chat clients consume one structured event protocol and render markdown correctly regardless of chunk boundaries.
  • Bot sessions are capped at 20 interactions without races, and follow-up suggestions are checked against the knowledge base.

What I learned

Streaming bugs are framing bugs. Decide what a complete message is before deciding how to render it.
